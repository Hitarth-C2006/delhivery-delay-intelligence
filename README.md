# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone for the AI and Machine Learning Certification Program, E&ICT Academy, IIT Roorkee.

The regional ops head has three questions. How long will a parcel take? Which parcels will miss their promise? Which hubs need which playbook? This repo answers all three in one chain. Part A cleans the raw export. Part B predicts delivery hours. Part C flags parcels likely to be late. Part D groups the 24 hubs and turns a batch of new parcels into an action list.

The data is synthetic. It all comes from `generate_data.py` (committed exactly as given in the brief). No real Delhivery records are used.

Every number below is copied from a CSV in `outputs/`. File names are in brackets so you can check them.

## Repository map

## How to run

From a fresh clone, in this order (Windows shown; on macOS/Linux use `source .venv/bin/activate`):

```bash
git clone https://github.com/Hitarth-C2006/delhivery-delay-intelligence.git
cd delhivery-delay-intelligence
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48 (the data files are already committed; this rewrites the same contents)
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

Notes:

- I built and ran this on Python 3.13 with the exact versions in `requirements.txt` (pandas 2.2.3, numpy 2.1.3, scikit-learn 1.5.2, joblib 1.6.0).
- **`models/delay_model.pkl` is regenerated by running `python package_model.py`.** The committed pickle only loads reliably on the scikit-learn version pinned in `requirements.txt`. If your installed versions differ, re-run `package_model.py` instead of loading the committed pickle.
- Every script reads only files inside the repo and runs offline. All random seeds are the ones the brief pins. Running `predict_delay.py` twice gives a byte-identical `outputs/new_shipment_actions.csv`.
- `part_c_classification.py` prints two warnings from SciPy/NumPy (`Unknown solver options: iprint` and `invalid value encountered in cast`). They're deprecation noise from newer SciPy and don't change any result.

## Data findings

Cleaning first (`part_a_checks.csv`). The raw export had 1224 rows. 24 were exact duplicates, which leaves 1200 parcels. `service_type` came in 12 spellings and is down to 3 after strip + title case. 5 parcels had the 999 kg scanner-fault weight, so those were treated as missing. Gaps were filled with medians: distance 314.95 km, weight 1.83 kg, declared value INR 1,121.50. After that there are 0 missing cells in the 17 features and the target. 278 of the 1200 parcels were late, a delay rate of 0.2317.

**(i) Express is late most often.** 119 of 243 Express parcels missed their promise, a delay rate of 0.4897. Standard is at 0.2056 and Economy at 0.0857 (`part_a_delay_by_group.csv`). The mean Express parcel takes 36.8056 hours against a 36-hour promise. So the average Express parcel is already late. That reads less like a model problem and more like the promise being set too tight.

**(ii) Delay rate climbs with hub tier.** Tier 1 hubs are late 0.04 of the time, Tier 2 0.215 and Tier 3 0.44. That's 16, 86 and 176 late parcels out of 400 each, so Tier 3 is 11 times Tier 1.

**(iii) Distance is the strongest single driver.** Delay rate goes 0.0219 (0-200 km) → 0.1368 (201-400) → 0.4364 (401-600) → 0.8523 (601+). In the 601+ band, 75 of 88 parcels were late.

**(iv) Top three correlations with `delivery_hours`** (`part_a_correlations.csv`, ranked by absolute value, `delivery_hours` itself excluded):

| Column | Correlation |
|---|---|
| `promised_hours` | 0.8372 |
| `distance_km` | 0.4013 |
| `n_stops` | 0.3247 |

`promised_hours` tops the list because it stands in for service type, and Economy parcels simply take longer. `hub_daily_capacity` comes right after at -0.3237: bigger hubs are faster.

**(v) Why `declared_value_inr` was log-transformed.** On the median-filled column the mean is INR 1,533.05 (1533.0542) and the median is INR 1,121.50. A mean that far above the median means a long right tail of expensive parcels. After the log, mean and median are 7.0277 and 7.0224, almost equal, so the column is roughly symmetric and a few costly parcels no longer dominate it.

One more check from the same file: delivery hours have Q1 = 43.255 and Q3 = 72.5625. The 1.5 × IQR fences are -0.7063 and 116.5238 hours, and only 1 parcel sits outside them. So there are no extreme outliers to deal with.

## Model results (regression)

Split 840 / 180 / 180 (`part_b_checks.csv`). The scaler was fitted on training rows only. Scaled training columns have a max absolute mean of 0.0 after rounding, while scaled test columns show 0.2187. If the scaler had seen the test rows, that second number would also be near zero.

**Baseline.** Predicting the training mean for every validation parcel gives R² = -0.0212 (`part_b_metrics.csv`). It explains nothing, and is a hair worse than using the validation set's own mean. Any real model has to clear 0.

**Validation results** (`part_b_metrics.csv`):

| Model | MAE | RMSE | R² |
|---|---|---|---|
| mean_baseline | 15.7952 | 18.8552 | -0.0212 |
| linear_regression | 3.9222 | 4.8912 | 0.9313 |
| decision_tree (depth 6) | 5.0971 | 6.2796 | 0.8867 |
| random_forest | 4.2882 | 5.5095 | 0.9128 |
| gradient_boosting | 3.9166 | 4.9165 | 0.9306 |

Linear regression won on validation with RMSE 4.8912 hours. Gradient boosting was 0.0253 hours behind, which is about a minute and a half. Following the brief's rule, linear regression was the one model scored on the test set: RMSE 4.5235 hours, R² 0.9493.

**Tree depth: bias vs variance** (`part_b_tree_depth.csv`). Depths 1 to 3 are high bias. Both errors are high and close together: depth 1 has train 11.6334 vs val 12.1324, a gap of only 0.499, and depth 3 is 7.5295 vs 8.7033. The tree is too simple to fit even the training data. Depth 6 is the sweet spot, with the lowest val_rmse of 6.2796. From depth 8 on it turns into high variance: train error keeps falling (3.336 at 8, 1.3613 at 12, 0.0 with no limit) while val error goes back up (6.7901, 7.354, 7.8368). With no limit the gap is 7.8368 hours. The tree memorises the training parcels and doesn't generalise.

**Learning rate** (`part_b_gb_learning_rate.csv`). 0.1 was best (val R² 0.9306). At 0.01 each tree takes such a small step that 100 trees cover only part of the distance, so it's still underfitting (R² 0.7127). At 1.0 each tree takes a full step, overshoots, and the next tree has to correct it. Errors bounce around instead of settling (R² 0.844).

**Cross-validation vs validation** (`part_b_cv.csv`, 5-fold on the 1,020 train + validation rows, one shared `KFold(shuffle=True, random_state=42)`):

| Model | mean R² | std R² |
|---|---|---|
| linear_regression | 0.9261 | 0.0048 |
| gradient_boosting | 0.9353 | 0.0045 |

The two rankings disagree. Validation puts linear regression first by 0.0253 hours of RMSE. CV puts gradient boosting first by 0.0092 of R². **I'd ship gradient boosting.** The validation win comes from one split of 180 parcels and is tiny. CV averages five splits over more than 5 times as many rows, and both spreads are about 0.005, so a 0.0092 gap there means more. Trees can also pick up interactions, like sale week hitting Express parcels harder, that a plain linear model can't learn without hand-made terms. Before rollout I'd refit it on all 1,020 rows and check it on fresh data. I didn't score it on this test set, because the test set was already used once for the brief's final model.

## Model results (classification)

Stratified split 840 / 180 / 180 with 195 / 42 / 41 late parcels.

**Validation results at the default 0.5 rule** (`part_c_models.csv`):

| Model | TN | FP | FN | TP | Accuracy | Precision | Recall | F1 |
|---|---|---|---|---|---|---|---|---|
| blind_all_on_time | 138 | 0 | 42 | 0 | 0.7667 | 0.0 | 0.0 | 0.0 |
| logistic_regression | 128 | 10 | 7 | 35 | 0.9056 | 0.7778 | 0.8333 | 0.8046 |
| decision_tree_depth_6 | 128 | 10 | 11 | 31 | 0.8833 | 0.7561 | 0.7381 | 0.747 |
| random_forest_default | 132 | 6 | 11 | 31 | 0.9056 | 0.8378 | 0.7381 | 0.7848 |

**The blind baseline is 0.7667 accurate and completely useless.** It says "on time" for everyone, so it catches 0 of the 42 late parcels. Ops can't call a customer about a parcel the model never flags. This is why accuracy alone isn't enough here, and why the rest of Part C watches recall and F1.

**Which columns carry signal?** (`part_c_feature_scores.csv`). The seven highest F-scores are `distance_km` (389.2131), `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag` and `sale_event_flag` (36.7281). All five bookkeeping columns fall outside the top 7. Their ranks are 8, 12, 14, 16 and 17, and their F-scores are all below 5. But the default forest still gives them a combined importance of 0.2245 (0.046 + 0.0374 + 0.0476 + 0.0499 + 0.0436), close to a quarter of the total. That's a known bias of impurity-based importance: columns with many distinct values give the trees lots of random split points, so they collect importance even when they're pure noise. The F-test doesn't fall for it. Same file, another quirk: `hub_tier` has F-rank 2 but forest importance of only 0.0399. It carries the same information as `hub_daily_capacity`, so the forest splits the credit between the two.

**The k table** (`part_c_selectk.csv`): val F1 is 0.6988 at k=5, 0.8333 at k=7, 0.7857 at k=10, 0.8049 at k=12 and 0.7848 at k=17. k=5 drops `rain_flag` and `sale_event_flag`, which are real causes, and F1 falls. k=7 is exactly the seven signal columns and it's the best. Adding weak and noise columns past that point only gives the forest more ways to overfit.

**Tuning** (`part_c_tuning.csv`, 7 selected columns, selector fitted on training rows only):

| Search | Candidates | Fits | Best params | CV accuracy | Val F1 |
|---|---|---|---|---|---|
| grid_search | 27 | 135 | n_estimators=100; max_depth=6; min_samples_leaf=1 | 0.8952 | 0.775 |
| randomized_search | 9 | 45 | n_estimators=50; max_depth=6; min_samples_leaf=1 | 0.8905 | 0.7848 |
| default_forest_same_7_features | 1 | 1 | n_estimators=100; max_depth=None; min_samples_leaf=1 | | 0.8333 |

Tuning did not beat the untuned forest on validation. Two reasons. First, both searches scored candidates on accuracy (the default), not on F1 or recall. Accuracy rewards saying "on time" since roughly three quarters of parcels are on time, so the searches settled on shallower depth-6 forests that are more cautious about calling a parcel late. Second, the validation set has only 42 late parcels, so one parcel moves recall by about 0.024. The gaps between 0.775, 0.7848 and 0.8333 come down to a handful of parcels. Picking a winner on a 180-row validation set is partly luck. Next time I'd run the search with `scoring="f1"` or `"recall"` so the CV measures what ops actually cares about. Under the brief's tie rule, the final model is the default forest on the 7 columns (`part_c_final_config.csv`).

**Alert threshold** (`part_c_thresholds.csv`). The ops rule is the highest threshold where validation recall stays at least 0.80. That's **0.5**:

| Threshold | Precision | Recall | F1 |
|---|---|---|---|
| 0.4 | 0.74 | 0.881 | 0.8043 |
| **0.5** | **0.7955** | **0.8333** | **0.814** |
| 0.6 | 0.8889 | 0.7619 | 0.8205 |

Going up to 0.6 would make the alerts cleaner (precision 0.8889) but recall drops to 0.7619, below the 0.80 floor. Because a missed late parcel costs more than an extra call, 0.6 is out. At 0.5 we catch 35 of 42 late parcels for 9 unnecessary calls. Side note: this row's F1 (0.814) is a bit below the 0.8333 in the tuning table. The tuning table uses `predict()`, which needs probability strictly above 0.5, while the ops rule uses ≥ 0.5. Two validation parcels sit at exactly 0.50. Both were actually on time, so under the ≥ rule they become two extra unnecessary calls.

**One test evaluation** (`part_c_final_test.csv`, threshold 0.5): TN 125, FP 14, FN 10, TP 31. Precision 0.6889, recall 0.7561, F1 0.7209, accuracy 0.8667.

To be straight about it: test recall (0.7561) came in below validation recall (0.8333) and below the 0.80 target. The test set has only 41 late parcels, so each one is worth about 0.024 of recall, and the gap is about 3 parcels. Some drop is normal, since the threshold was picked on the validation set and that number is a bit optimistic. I did not go back and change the model or threshold after seeing this. But if 0.80 recall is a hard requirement, 0.4 gives more headroom (validation recall 0.881) at the cost of more calls. That's the first thing I'd revisit when retraining.

## Operations recommendation

**Escalate segment.** 9 hubs, mean delay rate 0.46 (`segment_profile.csv`, `hub_profile.csv`):

| Hub | City | Tier label | Delay rate |
|---|---|---|---|
| HUB19 | Guwahati | 3 | 0.62 |
| HUB24 | Agartala | 3 | 0.54 |
| HUB20 | Raipur | 3 | 0.48 |
| HUB13 | Nagpur | **2** | 0.46 |
| HUB17 | Patna | 3 | 0.46 |
| HUB23 | Siliguri | 3 | 0.44 |
| HUB21 | Bhubaneswar | 3 | 0.40 |
| HUB18 | Ranchi | 3 | 0.38 |
| HUB15 | Kochi | **2** | 0.36 |

The Watch segment (8 hubs) runs at 0.155 and Standard (7 hubs) at 0.0257.

**Hubs whose tier label is wrong** (`tier_vs_segment_mismatch.csv`):

- **HUB07 Kolkata.** Labelled Tier 1, behaves like Watch: delay rate 0.14, 304.736 km average lanes, 70.76 stops. That's a Tier 2 profile.
- **HUB13 Nagpur.** Labelled Tier 2, behaves like Escalate: delay rate 0.46, 473.32 km, 83.92 stops.
- **HUB15 Kochi.** Labelled Tier 2, behaves like Escalate: delay rate 0.36, 466.514 km, 84.1 stops.
- **HUB22 Dehradun.** Labelled Tier 3, behaves like Watch: delay rate 0.2, 316.738 km, 73.28 stops.

What this means: the tier label describes size and capacity, not how the hub actually performs. For choosing a playbook, use the segment, not the tier. Nagpur and Kochi need Escalate-level attention even though their label says Tier 2. One more catch: the classifier uses `hub_tier` as a feature, so for these four hubs it's being fed a misleading input. The new batch shows it. Nagpur parcels scored 0.47 and 0.42 and Kochi parcels 0.31 and 0.37 (`new_shipment_actions.csv`), all just under the 0.5 line. I'd fix the labels, or swap `hub_tier` for the segment in the next model version.

**How good the alerts are.** At the 0.5 threshold, on the held-out test set (`part_c_final_test.csv`):

- Precision 0.6889: about **7 of every 10 flagged parcels are really late**. The other 3 calls are wasted, which the brief says is acceptable.
- Recall 0.7561: about **7 to 8 of every 10 late parcels get caught** before they're late.

**Today's batch** (`new_shipment_actions.csv`). 8 of the 48 new parcels are flagged. 6 of those are at Escalate hubs and need a **hub-manager escalation** (Agartala, Ranchi, Patna, Raipur, and Bhubaneswar twice). The other 2 get a **proactive customer call** (Dehradun and Jaipur, both Watch hubs). The remaining 40 need no action.

**Why K = 3** (`part_d_separation.csv`):

| K | Across / within distance ratio | Cluster sizes |
|---|---|---|
| 2 | 2.894 | 15-9 |
| 3 | 5.3928 | 9-8-7 |
| 4 | 6.3047 | 8-7-5-4 |
| 5 | 6.8866 | 8-7-4-3-2 |

The ratio keeps rising with K, but that's partly built in: more clusters means smaller clusters, and pairs inside a small cluster are always close. The big jump is from K = 2 to K = 3. After that the gains shrink. More to the point, K = 4 has a cluster of only 4 hubs, and K = 5 has clusters of 3 and 2. A group of 2 to 4 hubs is too small to justify its own playbook, and ops runs exactly three. K = 3 gives three solid groups of 9, 8 and 7.

## Production plan

**(a) Production-readiness, mapped to the repo**

| Characteristic | Where it lives |
|---|---|
| Accuracy | `outputs/part_c_final_test.csv`: one untouched test set, scored once at the chosen threshold. Same for the regression's test row in `part_b_metrics.csv` |
| Reliability | `outputs/part_d_reload_check.csv`: the reloaded pickle matches the in-memory model on all 180 test rows (max difference 0.0). `predict_delay.py` fills missing distance, weight and value with stored medians, so a blank field doesn't crash scoring |
| Reproducibility | `requirements.txt` pins exact versions, every `random_state` is fixed, `generate_data.py` is unchanged, and `.gitattributes` forces LF line endings so CSVs are byte-stable across Windows and Linux. Re-running `predict_delay.py` gives a byte-identical file |
| Performance (speed) | Scoring is one `predict_proba` call on a 7-column forest, so `predict_delay.py` finishes almost instantly. The full rebuild, both hyperparameter searches included, takes under a minute on a laptop CPU, with no GPU or paid service |
| Maintainability | `src/shipment_prep.py` holds `PROMISED_HOURS`, `FEATURES` and the two prep functions in one place. Each Part is its own script with one job |
| Consistency | `predict_delay.py` imports the same `clean_shipments` and `build_features` used in training, uses `models/impute_values.csv` for the fill values, and reorders columns by `models/feature_order.csv`. There's no second copy of the cleaning logic |
| Monitorability | `outputs/new_shipment_actions.csv` logs probability, flag and action per parcel. Join it to the real outcome later to measure live precision and recall |

**(b) What to monitor, with triggers**

| Quantity | Baseline | Trigger |
|---|---|---|
| Weekly delayed share of delivered parcels | 0.2317 (`part_a_checks.csv`) | Outside 0.16 to 0.30 in a non-sale week |
| Weekly share of parcels flagged | about a quarter (44 of 180 validation parcels flagged at 0.5, `part_c_thresholds.csv`) | Below 0.15 or above 0.35 for a week |
| Recall on parcels whose outcome is now known | 0.7561 on test, 0.8333 on validation | 4-week rolling recall below 0.70: re-check threshold and retrain |
| Precision on the same parcels | 0.6889 on test | Below 0.55: too many wasted calls, re-check threshold |
| Missing `distance_km` in the raw feed | 36 of 1200 (`part_a_checks.csv`) | Above 0.05 of a week's parcels: data-feed problem, fix before trusting scores |
| Hub mean lane distance | per hub in `hub_profile.csv` | Any hub moves more than 15% for two weeks: re-run Part D |

**(c) Retraining, the sale window, and drift**

Retrain monthly on a rolling window of recent delivered parcels. Pick the threshold again on a fresh validation slice each time, and re-run Part D segments every quarter. Make sure each training window contains at least one sale event. Otherwise `sale_event_flag` is constant during training and the model can't learn the sale effect.

The 15-28 September sale window needs its own comparison. During a sale, delay share and flag share will jump. That's expected, not drift. Compare a sale week against the previous sale event (or the sale-flagged rows of the training data), never against an ordinary week. Otherwise every sale sets off false drift alarms, and a retrain on sale-heavy weeks would teach the model that every week is a sale.

What real drift would look like here:

- The service mix shifting toward Express.
- More COD.
- Hubs taking on longer lanes or more stops (their profile drifting away from `hub_profile.csv`).
- Rain share falling. The training data covers July to September monsoon, and rain_flag is common in it, so an October-to-January model will see much less rain.
- A new hub ID that isn't in `hubs.csv`.

The first sign is usually the flag share and the live delayed share moving apart, for example more parcels flagged without more parcels actually arriving late.

## Limitations

1. **Synthetic data.** The generator is a clean additive formula with Gaussian noise. Real deliveries have failed attempts, returns, address problems and long-tailed delays that this data doesn't have, so real-world scores will be lower.
2. **Small test set.** Only 41 late parcels in test, so each one moves recall by about 0.024. The 0.7561 test recall has wide uncertainty, a few parcels either way.
3. **Threshold tuned on one validation split.** 42 late parcels decided between 0.5 and 0.6. A different split could pick a different threshold. Cross-validated thresholds would be steadier.
4. **Wrong tier labels feed the model.** `hub_tier` is a model input, and it's wrong for HUB07, HUB13, HUB15 and HUB22. Parcels from Nagpur and Kochi score just under the threshold partly because of this.
5. **Only one season.** About three months of July to September data, one sale event and monsoon weather. Nothing here says how the model behaves in winter or during Diwali-type peaks.
6. **No guard for unseen categories.** A hub missing from `hubs.csv`, or a new service type, would leave NaN features and stop `predict_delay.py`. Production needs an explicit check and a fallback.
7. **Version-locked pickle.** `delay_model.pkl` is tied to scikit-learn 1.5.2. Any upgrade means re-running `package_model.py`.
